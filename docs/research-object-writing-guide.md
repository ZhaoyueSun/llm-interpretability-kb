# Research Objects 节点介绍写作与检查准则

本文档面向后续维护 Research Objects taxonomy 的研究与数据 agent。目标是让不同时间新增或修改的节点保持一致的概念粒度、研究价值和双语质量，而不是把介绍写成字段注释、分类指令或前端说明。

## 一、节点介绍要回答什么

一段合格的介绍通常用两至四句自然语言回答以下问题；不要求机械地逐项列出，但不能缺少理解该对象所需的信息。

1. **对象是什么**：说明它是数据单元、激活状态、方向、组件、参数、关系结构还是动态过程。
2. **对象怎样形成**：如果来源并不显然，说明它由模型前向计算产生、由训练学习得到，还是由某种分析过程从激活或参数中估计出来。
3. **对象在模型中怎样存在或变化**：说明其所在空间、适用尺度以及与具体输入、位置、层、时间步或训练阶段的关系。
4. **研究者为什么研究它**：指出围绕该对象最自然的机制问题，以及相关观察能够支持到什么程度的结论。

介绍应当让没有打开父节点、相邻分支或 Techniques 页面的人也能理解当前节点。

## 二、先确定对象的本体类型

写作前先判断节点究竟指向哪一类实体。不同类型需要回答的问题不同。

| 对象类型 | 判定标准 | 介绍中应优先说明 |
|---|---|---|
| Data Unit | 输入中可直接观察或离散索引的单位 | 单位是什么，以及改变它对应什么实验问题 |
| Representation State | 模型处理具体输入时产生的激活值 | 出现在哪个位置、层或时间步，承载和传递什么信息 |
| Direction / Learned Feature | 在表征空间中估计或学习出的方向、坐标或子空间 | 如何获得，以及投影、激活或干预具有什么含义 |
| Score / Prediction | 模型在决策或生成边界上产生的量 | 输出的数学含义，以及比较、分解或追踪它能回答什么问题 |
| Native Component | 由模型架构和参数定义的内部计算结构 | 读取什么、执行什么运算、产生什么，以及因果贡献是什么 |
| Model Parameter | 训练学习并在推理时决定计算方式的数值量 | 参数结构、局部参数集合或参数变化与行为之间的关系 |
| Composed Mechanism | 多个内部对象通过连接和因果关系形成的联合结构 | 参与变量、信息路径、组合方式，以及必要性、充分性和忠实性 |
| Learning Process | 随训练或优化时间定义的动态对象 | 什么在变化、变化阶段或动力学是什么，以及为何形成最终机制 |

不要仅凭论文使用了某种方法来确定对象类型。例如，probe 是读出方法；它所读取的 activation state 才是对象。SAE、transcoder、crosscoder 或 ICA 可以作为 learned feature 的来源，但介绍不应把这些方法本身改写成对象。

## 三、说明来源，但不要写分类树说明

当一个对象不是模型中显然存在的原生量时，必须交代其来源。

- 对 Linear Direction，应先说明向量 \(v\) 是从激活空间中估计或构造出来的；来源可以是对比样本的平均激活差、线性读出权重或针对行为优化的干预方向。
- 对 Learned Feature，应说明它由辅助分解从模型激活或组件的输入—输出关系中学习得到；可以列举 SAE、transcoder、crosscoder 或 ICA 作为来源。
- 对 Parameter Delta，应定义比较的模型状态，例如 \(\Delta\theta=\theta_{\mathrm{after}}-\theta_{\mathrm{before}}\)。

方法名称只用于解释对象怎样产生，不要写“该方法属于 Techniques 分类树”“应归入某分支”之类的维护信息。介绍面向研究者解释概念，taxonomy 之间的边界由数据结构和维护文档负责。

## 四、保持节点自洽

节点介绍应定义自己，而不是依赖跨分支比较。

避免以下写法：

- “与 Native Model Components 相比……”；
- “本分支区分……”；
- “为了避免架构名称成为树根……”；
- “这种论文应归入该节点……”；
- “字段表示……”或其他类似代码注释的表述。

只有在相邻概念确实容易混淆、且区别构成对象定义的一部分时，才做局部对照。例如 Token 与 Token Embedding、Feature Map 与 Channel / Filter 可以简短区分；不应为了说明 Representation State 而跳到远处讨论 Component 分支。

## 五、父节点与叶节点的粒度

- **父节点**说明一组对象共享的本质、共同的研究问题和证据边界。不要逐项复述全部子节点，也不要解释为什么这样组织树。
- **叶节点**说明该对象区别于同级对象的形成方式、数学结构或功能角色。必要时给出一至两个代表性例子，但不要把介绍写成论文或方法名单。
- 父子节点应当逐层收窄含义。若叶节点介绍只是重复父节点，说明粒度尚未写清；若父节点只罗列子节点，说明缺少共同概念。
- 不要用同一个对象的 input、internal、output 角色创建重复定义。角色由 `applicable_object_roles` 表达。

## 六、公式与符号

公式只在能够消除歧义或揭示对象结构时使用。

- 首次出现符号时先说明其来源。例如在写 \(v^\top h\) 前，应说明 \(v\) 是激活空间中的方向，\(h\) 是模型状态。
- 使用 `\(...\)` 表示行内公式，使用 `$$...$$` 表示确有必要的块级公式。
- 优先使用语义明确的记号，例如转置写作 \(^\top\)，不要突然出现未定义的 \(v\)、\(h\)、\(A_t\) 或 \(\theta\)。
- 公式之后要解释其研究含义；公式不能替代概念说明。
- 不为显得技术化而添加公式。能够用一句清楚自然语言表达的内容无需数学包装。

## 七、谨慎描述证据强度

介绍应帮助读者区分“可以观察到”与“已经证明模型使用”。

- 可解码或投影相关说明信息可以从该对象中读出，不自动证明模型因果使用该信息。
- 激活选择性、attention pattern、saliency 或 attribution score 可以提出候选机制，不自动构成完整机制解释。
- 干预导致行为变化能够加强因果主张，但仍需考虑选择性、替代路径和副作用。
- Circuit 或 Composed Mechanism 的强主张通常需要必要性、充分性与 faithfulness 检验。
- Learned Feature 的语义清晰度不自动保证其重构忠实性或下游因果作用。

限制说明应与当前对象直接相关，不要给每个节点机械地追加同一句“仍需因果验证”。

## 八、架构与模型族

Research Objects 主树默认使用跨架构语言。只有对象确实由特定架构定义时，才在介绍中使用 Transformer、CNN、RNN、State-Space、MoE 或 Diffusion 等术语。

- 架构适用范围写入 `applicable_model_families`，不要把模型族变成对象定义的一部分。
- 通用父节点应使用能覆盖多个模型族的表述。
- 架构特化叶节点可以使用该架构的标准术语，并解释其在计算中的具体含义。
- 示例不应无意中把 Transformer 当作所有神经网络的默认模型。

## 九、中英文质量

- 英文和中文应保持概念、范围、例子与证据强度一致，但不要求逐句直译。
- 两种语言都应像面向研究人员的短篇讲解，而不是 schema 字段说明。
- 标题只维护英文版本；中文介绍可以保留领域内已普遍使用的英文术语，如 attention head、residual stream、feature map 与 steering vector。
- 中文句子优先使用自然语序，不因 YAML 换行产生多余空格或割裂短语。
- 英文避免用 `This branch contains...`、`This node is used for...` 等分类说明式句型。
- 专有术语、公式符号和证据强度在中英文中必须对应，不能一侧加入另一侧没有的重要限定。

## 十、推荐写作模板

模板用于检查信息是否完整，不要求所有节点使用相同句式。

### 原生对象

> **[Object]** 是由模型的 **[架构、参数或前向过程]** 定义的 **[对象类型]**。它在 **[尺度或位置]** 上执行、承载或产生 **[作用]**。研究通常关注 **[两个或三个核心问题]**。

### 分析得到的对象

> **[Object]** 是从 **[原始激活、参数或组件关系]** 中通过 **[估计或学习方式]** 得到的 **[方向、特征或结构]**。**[观测量或公式]** 表示 **[研究含义]**。研究还需区分 **[可观察证据]** 与 **[更强的因果主张]**。

### 组合或动态对象

> **[Object]** 描述 **[多个内部对象]** 如何通过 **[连接、因果关系或时间演化]** 形成 **[计算、行为或训练结果]**。研究通常识别 **[组成与变化]**，并检验 **[相应证据标准]**。

## 十一、提交前检查清单

逐项回答“是”后，节点介绍才可进入提案：

- [ ] 第一遍阅读即可判断对象是什么类型的实体。
- [ ] 非显然对象说明了从哪里、通过什么方式产生。
- [ ] 介绍说明了研究该对象能够回答什么问题。
- [ ] 所有公式符号在使用前或使用时得到解释。
- [ ] 没有把 technique、模型族、论文贡献类型或可视化控件误写成对象。
- [ ] 没有“属于另一棵树”“本分支用于”“应归入”等分类维护说明。
- [ ] 没有依赖远处节点才能理解的跨分支比较。
- [ ] 父节点不是子节点清单，叶节点也没有简单重复父节点。
- [ ] 证据措辞没有把相关、可解码或局部敏感性夸大为因果机制。
- [ ] 英文和中文在对象范围、例子、公式与限制上语义一致。
- [ ] 标题保持英文，`node_id` 和既有父子关系没有被文案修改意外改变。
- [ ] 介绍不含本机路径、实现细节或临时研究备注。

## 十二、正式更新流程

1. 阅读当前节点、父节点、直接子节点、相邻节点以及关联论文，先确认问题属于文案质量还是结构问题。
2. 同时起草英文和中文介绍，并用本指南的检查清单自审。
3. 文案实质修改先写入 `data/classification-proposals.yaml`，列明受影响节点、修改理由和版本变化。
4. 获得用户明确批准后，更新节点 `introduction` 与 `proposal_id`，并递增 taxonomy 版本。
5. 如果只是文案澄清且对象范围不变，不重写论文分类事件；若节点范围改变并影响论文归属，必须另建 classification proposal。
6. 校验 YAML、节点 ID 唯一性、父节点引用、双语介绍完整性，以及现有事件对节点的引用。
7. 将本次批准改动作为独立 Git commit 推送，不混入其他阶段或尚未批准的修改。

本指南约束的是节点介绍质量。节点新增、移动、合并、废弃或范围变化仍须遵循项目的 taxonomy 提案与审批规则。
