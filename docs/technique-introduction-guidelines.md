# Techniques 节点介绍写作与审核准则

本文档约束 `data/taxonomies/techniques.yaml` 中英文标题下的中英文 `introduction`。目标是让不熟悉某项技术的研究者也能理解：它要回答什么问题、具体怎样做、结果能支持什么判断，以及不能据此推出什么。

这是面向后续数据维护者和 agent 的执行准则，不是面向网页读者的 taxonomy 正文。

## 1. 写作定位

- 读者是对机制可解释性有研究背景、但可能不熟悉该技术的研究者。
- 介绍应是简短的研究者导读，不是字段说明、代码注释、论文摘要或术语表。
- 首先解释科学问题和方法直观，再引入必要术语、算法步骤或数学对象。
- 不设硬性字数；以完整说清方法为准，删除不帮助读者理解或判断证据的内容。

## 2. 更新前必须阅读的上下文

撰写或修订一个节点前，必须同时检查：

1. 当前节点的标题、父节点、子节点和相邻易混淆节点；
2. 当前事件流中分到该节点的 primary 和 secondary 论文；
3. 这些论文的方法、验证和证据边界，而不只是标题或 abstract；
4. 支撑该方法家族的本地综述或外部主要论文，尤其是 corpus 中尚无主论文的 external-reference 叶节点。

介绍应概括节点的方法家族，不得只照顾其中最知名的一篇论文。论文数量与 corpus 覆盖情况不得反过来限定技术的学术含义。

## 3. 父子节点的写作分工

### 3.1 父节点

父节点应解释子方法共同回答的问题、共享的操作逻辑和总体证据边界。它应让读者理解“为什么这些方法属于同一家族”，但不应：

- 逐个重复子节点的定义；
- 用一句话枚举所有子节点代替解释；
- 把小类与不在同一层级的大类强行比较；
- 写入“父节点不放论文”、论文数量或分类规则等内部管理信息。

如果父节点需要说明子方法之间的关系，应围绕一条共同流程自然展开，而不是复制子节点标题。

### 3.2 子节点和叶节点

子节点应继承父节点已经建立的问题，进一步回答：

1. 它直接处理什么输入、模型状态或参数；
2. 研究者具体执行什么操作；
3. 产生什么分数、方向、子空间、字典、子图或反事实结果；
4. 结果在什么条件下能支持什么判断；
5. 哪些混淆、假设或失败模式会限制该判断。

叶节点不能只重复父节点的动机。它必须增加足够的操作细节，使读者能区分该方法与其他叶节点。

### 3.3 层级与论文分类

- 具有子节点的节点只作为组织节点，不直接承载论文关系；相关论文必须分到至少一个能准确描述其技术贡献的最具体子节点，不能只停留在父节点。
- 如果父节点下包含理论形式化工作，必须保留对应的具体子分支，不得让理论论文只停留在父节点。
- 一篇论文可以同时使用多种 technique，因此可以属于多个叶节点；不得为了强制互斥而扭曲节点定义。
- 若一个中间节点只有一个子节点，应检查是否存在重要且技术上独立的外部方法；若不存在，考虑合并层级。
- 重要的 external-reference 叶节点即使 corpus 暂无论文也可保留，但介绍必须有可核验的方法依据。

## 4. 单个介绍的内容结构

建议按以下逻辑组织，但不要在正文中显示模板标签：

1. **问题**：这项技术直接想知道或改变什么；
2. **操作**：使用什么输入、中间状态、对照或参数，怎样处理；
3. **输出**：得到什么可观察结果，它如何被计算或验证；
4. **解释**：什么结果支持什么强度的结论；
5. **边界**：它不能单独证明什么，结论依赖哪些设计选择；
6. **关系**：只在容易混淆时，说明与相邻方法的区别或衔接。

开头应尽快出现句子主干。不要先堆积一串方法名、例子或限定语，再在段末才说该技术做什么。

## 5. 证据强度与措辞

介绍必须把“方法计算了什么”与“结果证明了什么”分开。下表是常用边界：

| 结果 | 通常可支持 | 不能单独证明 |
| --- | --- | --- |
| 激活统计、注意力模式或几何结构 | 某种内部模式存在 | 模型依赖它产生行为 |
| probe 成功 | 信息对所选读出器可访问 | 原模型在任务中使用了该信息 |
| 梯度或 sensitivity 分数 | 指定状态附近的局部变化率 | 大幅干预、非线性交互或唯一因果作用 |
| attribution 分数 | 按某种基线和记账规则分配的贡献 | 与规则无关的客观因果贡献 |
| 消融、替换或 patching 改变行为 | 该对象在指定干预和评价条件下具有功能作用 | 它是唯一、自然或完整的机制 |
| steering 成功 | 存在能够控制行为的操作入口 | 模型在自然运行时就以同样方式使用它 |
| 形式证明或反事实对应 | 在明确假设、映射和干预集下的结论 | 该假设自动适用于所有真实模型或存在唯一高层解释 |
| benchmark 优势 | 在指定数据、指标、预算和基线下表现更好 | 方法在所有任务上普遍更优 |

避免把“相关”、“可解码”、“局部敏感”、“干预有效”、“结构忠实”和“形式保证”写成同一强度的证据。

## 6. 技术关系必须说清

只有在解决真实混淆时才比较相邻方法。比较应围绕操作对象、计算过程、证据含义或研究目的，不得仅因名称相近就强行对比。审核时尤其检查：

- attention pattern 是 softmax 后的路由权重；QK score matrix 产生路由分数；OV 决定被读取信息如何写回 residual stream。
- attribution 按基线和规则分配预测贡献；sensitivity 测量局部小变化率；causal intervention 直接构造并比较反事实运行。
- probing 检验信息能否从表征中恢复，不自动说明原模型使用该信息。
- Feature Dictionary Learning 事后学习一套解释基底；Neural Feature-Learning Analysis 研究原网络自身如何在训练中形成特征。
- Causal-Abstraction Formalism 给出实现关系的定义和判据；Interchange Intervention 在给定对齐下执行反事实检验；DAS 搜索分布式对齐关系。
- Circuit Discovery 搜索和验证多组件子图；Causal Intervention 是它可使用的证据工具之一，不是同一层级的同义词。
- steering 以可靠控制行为为目的；相同操作在 Causal Intervention 中则以检验原模型机制为目的。
- Dictionary Quality Metrics 测量解释特征的质量；Optimization-Landscape Analysis 研究这些特征为何会由目标函数和优化过程形成。

## 7. 表达与术语

- 每句尽量只承担一个主要逻辑；先写句子主干，再补充方法变体或例子。
- 若一串顿号使读者无法看出这些项的共同作用，先用一句话概括，再将方法例子放入括号或后续句。
- 所有代词和范围词都应有明确指向。例如，不写“在 token 或数据集上统计”，而写“收集某个内部单元在不同 token 上的激活，并在大量样本上汇总”。
- 技术名不能代替操作解释。仅写“使用 patching”、“训练 decoder”或“计算 attribution”不够，必须说明 patch 什么、decoder 将什么映射到哪里、分数怎样得到。
- 普通概念优先使用易懂的中文；学界已稳定使用的方法名、缩写和容易在论文中检索的关键词可保留英文。首次出现的非通用缩写应给出全称。
- 对容易误解的英文词补充中文含义，例如将 `shrinkage` 说明为“收缩偏差”。
- “分支”可能指 taxonomy 分支、网络中的计算分支或并行模块；正文必须写明具体指什么。
- 公式只在它比纯文字更能澄清机制时使用，并在公式前后解释每个量的直观含义。

## 8. 介绍中不应出现的内容

以下内容属于内部数据管理，应写在提案、事件流或维护文档中，不得放入面向读者的 introduction：

- 节点下有多少篇论文；
- 论文必须分到父节点还是子节点；
- primary、secondary、proposal ID、taxonomy 版本或审批状态；
- “这个节点为了可视化而保留”等展示系统说明；
- 对更新者的操作指令或审核记录。

为避免误解而说明技术范围是允许的。例如，“本节点只讨论推理时的激活投影移除，永久修改权重属于 Parameter-Space Editing”是技术边界，不是数据管理信息。

## 9. 中英文一致性

- 先完成并审核中文逻辑；用户批准后，再撰写自然英文。
- 英文不做逐字直译，但必须与中文保持相同的技术范围、操作步骤、证据强度和限制条件。
- 不得只在某一语言中新增关键事实、实例、强因果措辞或重要保留条件。
- 方法名、缩写、对象名和证据术语在相关节点中保持一致。
- taxonomy 标题仅维护英文；中文 introduction 中可在首句复用英文标题以建立对应。

## 10. 修改与审批流程

1. 先读取当前 taxonomy、父子节点、相邻节点和已分类论文。
2. 先判断是文案问题还是结构问题。如果需要新增、移动、合并、拆分或重命名节点，必须先单独形成结构提案。
3. 向用户提供整段中文修订稿，不只解释局部句子或给出零散替换词。
4. 用户批准前不得修改正式 taxonomy。审核期间的讨论不等于写入授权。
5. 获得明确批准后，撰写对应英文，在 `data/classification-proposals.yaml` 记录批准依据、变更理由和受影响节点，并递增 taxonomy 版本。
6. 纯文案修改不改分类事件。只有论文—节点关系发生变化时，才向 `data/classification-events.jsonl` 追加 `assign`、`revoke`、`replace` 或 `confirm` 事件，不得改写历史。
7. 修改前后运行现有校验；检查 YAML/Schema、唯一 `node_id`、有效 `parent_id`、无循环树结构、事件节点引用和每篇论文的 primary 约束。
8. 重建网页派生数据，确认中英文切换、树层级、论文计数和节点绑定正常。
9. 只提交本次已批准文件，不得混入其他未批准或无关工作区变更。

## 11. 写入前检查清单

每个修订节点必须能对下列问题回答“是”：

- [ ] 第一两句已说清该技术要回答什么问题。
- [ ] 正文说明了研究者实际执行的操作，而不只是罗列方法名。
- [ ] 对输入、内部状态、参数、对照和输出的指代都明确。
- [ ] 已说明结果能支持的结论强度，且没有将相关、可解码或局部敏感夸大为因果证明。
- [ ] 已说明最重要的假设、超参数、基线、分布外风险或失败模式。
- [ ] 介绍继承了父节点，又比父节点提供了更具体的技术信息。
- [ ] 父节点没有逐条重复子节点，子节点也没有只重复父节点。
- [ ] 具有子节点的组织节点没有直接承载论文关系，相关论文已分到至少一个具体子节点。
- [ ] 与相邻方法的区别仅在必要时出现，且比较处于同一逻辑层级。
- [ ] 没有将 target object、research question、contribution role、evidence strength 或 modality 误当成 technique 定义。
- [ ] 没有论文数量、分类要求、提案或版本等内部管理语言。
- [ ] 中英文在事实、范围、证据强度和限制上一致，同时分别符合自然表达。
- [ ] 修订已有明确用户批准，并完成修改前后校验和可视化重建。
