# Research Question 写作与审核准则

本文档面向后续维护 Research Questions 数据的研究与数据 agent。目标是让新增论文、调整节点和更新当前进展时，始终保持一致的问题粒度、证据边界、双语质量和演化关系。图数据模型、关系类型和可视化契约见 `docs/research-question-graph-methodology.md`；本文聚焦具体写法与逐篇审核流程。

## 一、先保留两个层次的 Research Question

每篇论文必须区分两个层次，不得用其中一个替代另一个。

### 1. 论文级 RQ

论文级 RQ 忠实重构作者在正文中实际试图回答的问题，应保留：

- 研究对象；
- 关键条件与比较对象；
- 作者检验的主张；
- 实验或理论能够支持的证据边界。

论文级 RQ 可以较具体，可以包含模型、任务或方法，因为这些细节可能决定论文究竟提出了什么问题。提取时优先阅读引言中的研究缺口与目标、方法要验证的命题、实验设计和结论，而不是只看标题或摘要。

### 2. 标准化时间轴 RQ

标准化 RQ 是可视化中的节点。它应去掉可替换的模型名、数据集和实现细节，但保留真正的科学未知，使多篇论文能够围绕同一问题形成继承、挑战、扩展或分叉关系。

标准化不是把论文级 RQ 缩成宽泛主题。例如，“Sparse Autoencoders”“Circuit Analysis”“Learning Process”都不是合格 RQ；“稀疏自编码器能否从叠加表示中恢复可解释特征？”才是可回答的问题。

## 二、RQ 不等于研究对象、技术或应用

对每篇论文分别回答以下四个问题：

| 维度 | 判断问题 | 示例 |
|---|---|---|
| Research Object | 论文试图解释什么实体或过程？ | 神经元、残差状态、电路、训练轨迹 |
| Technique | 论文用什么操作获得证据？ | probe、activation patching、SAE、steering |
| Application | 论文在哪种行为或任务中检验？ | 事实召回、数学推理、多语言生成 |
| Research Question | 关于该对象，什么仍然未知？ | 可读出的信息是否真的被模型使用？ |

### 替换检验

- 替换 technique 后科学未知仍然成立：通常仍是同一个 RQ。
- 替换 application 后问题仍然成立：通常是同一 RQ 的跨领域证据，而不是新节点。
- 替换 research object 后需要不同机制解释或证据：可能需要拆成不同 RQ。
- 方法本身只有在论文研究其有效性、可靠性、边界或实用价值时，才能成为问题对象；标题仍应写成未知主张，而不是方法名称。

RQ 大类必须由论文的核心未知决定，不能从 Technique 分类机械映射。Readout 可以支持表示形式、时序学习、机制解释或证据标准；causal intervention 同样可以服务于全部七个大类。

## 三、先独立判断论文，再对照既有节点

为避免被现有分类锚定，审核一篇论文时按以下顺序进行：

1. 不看现有 RQ 大类，先从原文独立写出论文级 RQ。
2. 对照论文文件中的 `ai_summary`，检查研究问题、方法、实验和结论是否一致。
3. 若二者不一致，回到原文引言、研究目标、方法命题、实验设计和结论重新核对；摘要不能作为最终裁决。
4. 判断论文的主 RQ 属于哪个大类，再判断是否存在实质性的 secondary RQ。
5. 最后才与现有节点比较，决定合并、拆分、新增或只作为关联论文加入。

`ai_summary` 是导航和交叉检查材料，不是替代原文的事实来源。出现以下情况时必须重读全文相关段落：

- 标准化 RQ 比 AI summary 更强或更宽；
- 标题包含论文没有验证的因果、承诺、普遍性或有效性主张；
- 现有分类与论文的主要实验目标不一致；
- 一篇论文被用来支持多个相互独立的节点；
- 当前进展没有覆盖论文的重要负面结果或限制。

## 四、RQ 标题的写作标准

标题的作用是让读者一眼识别研究方向，而不是在一行内塞入整篇论文。

### 1. 标题必须是清楚、可回答的问题

优先使用以下基本形式：

- **是否 / Can / Does**：论文检验存在性、可行性、必要性或某个假设是否成立。
- **如何 / How**：论文研究过程、机制、形成方式或可操作方案。
- **为何 / Why**：论文解释一个已经确认存在的现象或转变。
- **何时 / When**：论文研究成立条件或适用边界。

不要把“是否”问题改写成预设结论的“如何”。例如，论文检验任务信息是否随深度变得更容易线性读出，标题应写“是否会变得更容易”，而不是默认趋势成立后再问“如何变化”。

### 2. 标题只保留决定研究方向的核心未知

坐标轴依赖、具体度量、替代基线、模型名称、数据集和实现细节通常放入介绍，而不放入标题。标题过长往往说明多个问题被错误合并。

例如：

| 不推荐 | 推荐 | 原因 |
|---|---|---|
| 当前内部状态提前承诺了多远的未来生成轨迹？ | 单个隐藏状态能提前读出多远的后续生成？ | 论文只证明可读性，没有证明因果承诺。 |
| 参数差分形成的任务向量能否支持行为的模块化删除、组合与迁移？ | 能否用参数任务向量删除或组合模型能力？ | 细节放入介绍，标题保留方向。 |
| 模型差分方法如何区分真实的后训练特征与稀疏优化伪影？ | 模型差分发现的新特征是真实变化还是方法伪影？ | 改成自然、可直接理解的问题。 |
| 在什么定义、对照和反事实约束下，一个解释才真正依赖被解释模型？ | 解释结果是否真正依赖被解释的模型？ | 证据条件放入介绍。 |

### 3. 不得把实验结论写成问题前提

- “是否更容易读出”可以作为待检验问题；“如何变得更容易读出”预设了趋势存在。
- “能否读出未来信息”不能写成“模型提前承诺未来计划”。
- “组件在两个任务中重合”不能直接写成“通用模块如何被复用”。

### 4. 中文必须符合自然阅读习惯

- 避免连续堆叠“统一、可公理化、可高效计算”等多个定语。
- 避免把英文名词结构逐词翻译成中文。
- 已普遍使用的术语可以保留英文缩写，但句子主体应是自然中文。
- 不用“某某工作”代指论文主题，如“IOI 工作”“算术工作”；优先写作者、论文标题、方法名或自然的研究对象。

## 五、节点介绍的写作标准

介绍回答“这个问题究竟在问什么”，不负责罗列论文结果。通常用两至五句完成以下内容：

1. 定义核心未知和研究对象。
2. 说明需要区分的相邻概念。
3. 说明什么证据能够回答该问题。
4. 必要时给一个具体例子，帮助读者理解抽象区别。
5. 明确该问题不包含什么，防止与相邻 RQ 或其他 taxonomy 混淆。

常见边界包括：

- 可解码性不等于因果使用；
- 局部化不等于最佳编辑位置；
- 找到相似组件不等于行为忠实；
- 表示可读不等于解释构造完成；
- 能够操纵输出不等于恢复了模型原有知识；
- 跨任务组件复用不等于独立模型形成相同机制；
- 跨模型特征迁移不要求两个模型的表示逐单元相同。

介绍中可以出现方法名来说明证据形式，但不能写成方法说明书，也不能把当前论文结论提前写入问题定义。

## 六、“当前进展”的写作标准

当前进展不是论文摘要拼接，而是围绕同一 RQ 的证据综合。必须覆盖节点下全部 primary papers，并只在确实推进该问题时纳入 secondary papers。

### 推荐结构

1. **起点**：最早论文提出了什么问题或建立了什么基线。
2. **推进**：后续论文增加了什么新对象、方法、因果证据或适用范围。
3. **当前结论**：现有证据共同支持什么，不支持什么。
4. **未解问题**：限制来自模型、任务、样本、方法假设、替代机制还是跨分布泛化。

### 写作要求

- 按问题发展顺序组织，不机械按论文逐篇列举。
- 用作者名、方法名或明确对象作为主语，避免“某某工作表明”反复出现。
- 写清楚证据类型：相关、读出、消融、干预、跨模型复现、形式证明或求解器证书。
- 负面结果也是进展，必须明确记录，而不是只写成功案例。
- 区分“在当前语料中得到支持”与“整个领域已经形成共识”。
- 不能从单模型、单任务或合成实验推出普遍规律。
- 一个论文只证明候选机制、局部作用或输出阶段时，不得写成恢复了完整机制。
- 对 `secondary_paper_ids`，应说明它提供的是补充、边界、反例还是相关但不同的证据，不能把它写成该节点的核心来源。

## 七、合并、拆分与论文归属

### 1. 合并条件

多个论文级 RQ 只有同时满足以下条件才合并：

- 核心未知谓词相同，如存在、形成、使用、控制、迁移或有效性；
- 主张范围兼容；
- 回答其中一个问题会实质性回答另一个。

### 2. 必须拆分的情况

即使论文使用相同技术、对象或术语，只要所需证据不同，就应拆分。例如：

- 信息可读出 vs. 信息被模型使用；
- 电路如何计算 vs. 如何自动发现该电路；
- 因果定位 vs. 定位是否预测最佳编辑位置；
- 同一模型跨任务复用组件 vs. 不同模型复现同一机制；
- 不同模型自然形成相同表示 vs. 通过映射把特征迁移过去；
- 训练中形成机制 vs. 推理深度中的演化 vs. 生成步骤中的演化；
- 特征重构质量 vs. 单义性 vs. 下游实际价值。

一个节点挂载过多主题不同的论文，或标题需要三个以上并列谓词，通常是应当拆分的信号。一个大类只有极少数宽泛节点时，也应检查是否压缩了独立研究分支。

### 3. Primary 与 secondary

- 每篇论文必须且只能有一个 `primary_paper_ids` 归属，表示论文的中心科学未知。
- 论文确实提出或回答额外问题时，可以出现在其他节点的 `secondary_paper_ids`。
- 仅共享 technique、research object、application、模型或数据集，不足以建立 secondary 归属。
- 不要为了让图更密而添加 secondary 论文或关系线。

## 八、七个大类的判定边界

| 大类 | 核心判断问题 |
|---|---|
| 表示形式 | 模型表示了什么，以什么结构或几何形式存在？ |
| 计算机制 | 模型为了产生行为，实际执行了什么计算和信息流？ |
| 机制解释 | 如何把内部状态或计算构造成可供人检查的解释？ |
| 干预与控制 | 如何利用内部机制稳定、选择性地改变模型行为？ |
| 时序学习 | 表示、预测、电路或能力如何随深度、生成步骤或训练形成和变化？ |
| 证据标准 | 什么证据足以支持解释、定位、因果、有效性或安全审计主张？ |
| 泛化与迁移 | 解释、机制或特征能否跨样本、任务、训练运行、模型和规模成立或迁移？ |

分类时以主 RQ 为准。一篇使用 causal intervention 的论文，可能研究计算机制、干预控制、证据标准或泛化迁移；不能因为技术相同就归入同一大类。

## 九、关系线的写作与检查

关系线表达研究问题如何演化，不表达论文仅仅共享对象、技术或应用。

### 1. 建边前提

- source 的 `first_date` 应早于 target；同日或时间不明确时要谨慎。
- target 必须对 source 的问题进行收窄、挑战、扩展、整合、验证、规模化或形式化。
- rationale 应明确写出“从什么问题推进到什么问题”，不能只写“两者相关”。
- 关系不能从论文主题相似自动推断。

### 2. 证据等级

- `direct-citation`：目标论文正文明确引用并实质性使用、检验、批评或扩展来源论文的问题；只有参考文献匹配不够。
- `same-lineage`：概念上是清楚的连续发展，但尚未确认正文中的实质引用。
- `analyst-inference`：由本图提出的综合关系，不能表述成论文作者明确主张的历史事实。

### 3. 关系说明不得超过论文证据

例如，Future Lens 只证明未来 token 信息可以从当前状态读出，因此关系说明应写“从未来信息读出推进到跨生成位置的因果追踪”，不能写“从未来承诺推进到……”。

## 十、首次时间的确定

`first_date` 使用最早真正提出该标准化问题的论文公开日期，而不是：

- 最早使用相关技术的论文；
- 最早研究相同对象的论文；
- 后续论文引用的更早背景文献；
- 只隐含前提、但没有提出同一未知的论文。

较早论文可以作为 secondary paper 或 source node，但只有已经提出相同科学未知时，才能把节点时间提前。

## 十一、双语一致性

- `question_en` 与 `question_zh` 的问题类型、范围和证据强度必须一致。
- `introduction_en` 与 `introduction_zh`、`progress_en` 与 `progress_zh` 应信息等价，但不要求逐句直译。
- 中文优先自然表达，英文优先清楚准确；不要为了形式对称制造拗口句子。
- 专有名词、模型范围、数量级和限制条件不得只在一种语言中出现。
- 英文使用较强词语，如 `causal`、`faithful`、`complete`、`universal`、`commit` 或 `guarantee` 时，必须确认中文和论文证据具有相同强度。

## 十二、标准审核流程

### A. 单篇论文

1. 阅读原文引言、研究目标、方法命题、主要实验和结论。
2. 独立写出论文级 RQ。
3. 与 `ai_summary` 中的 Research Question、Method、Validation 和 Conclusion 对照。
4. 确定一个 primary RQ，并记录可能的 secondary RQ。
5. 检查现有节点是否真正共享同一未知；不能只按关键词匹配。
6. 若发现不一致，记录原分类、建议分类、原文证据和修改理由。

### B. 单个 RQ 节点

1. 逐篇检查全部 primary 和 secondary papers。
2. 检查标题是否简洁、中性、可回答，并与论文的“是否/如何/为何/何时”一致。
3. 检查介绍是否定义问题、边界和证据，而非复述结果。
4. 检查当前进展是否覆盖全部 primary papers、重要负面结果和共同限制。
5. 检查是否与相邻节点重复，或是否把多个不同未知压进一个节点。
6. 检查中英文范围和强度是否一致。

### C. 单个大类

1. 不参考原分类，逐篇独立判断 primary family，再与现有分类对照。
2. 检查是否存在因技术或对象相同而造成的错误聚类。
3. 检查分支覆盖是否偏向某种模型、方法、任务或证据。
4. 对节点过少的类别检查是否发生过度合并；对节点过多的类别检查是否把实验细节误当成独立问题。
5. 检查类内演化与跨类关系是否能够解释“研究问题如何推进”，而不只是形成论文相似性网络。

## 十三、数据修改与校验流程

RQ 图当前维护在 `docs/research-question-graph-draft.yaml`。涉及标题、介绍、当前进展、论文归属、节点拆分合并或关系线的实质修改，应先向用户展示修订方案并获得批准。

修改前运行：

```bash
ruby scripts/validate_research_question_graph.rb
```

修改后至少运行：

```bash
ruby scripts/validate_research_question_graph.rb
git diff --check
conda run -n interpret-vis python scripts/build_web_data.py
```

并人工确认：

- [ ] 每篇 corpus 论文恰好有一个 primary RQ。
- [ ] secondary 归属均有实质问题联系。
- [ ] 每个节点有完整的中英文标题、介绍和当前进展。
- [ ] `first_date` 与最早提出该问题的论文一致。
- [ ] 新增、删除或拆分节点后，论文总覆盖没有变化。
- [ ] 每条边都有类型、证据等级和自然语言理由。
- [ ] `direct-citation` 已经检查正文语境，而非只匹配参考文献。
- [ ] 派生网页数据已重建，但没有被当作事实来源反写。
- [ ] Git 提交只包含本次已批准修改，没有混入其他阶段的工作。

## 十四、最终质量检查清单

只有以下问题全部回答“是”，RQ 修改才可以进入数据模型：

- [ ] 不看论文列表也能从标题一眼判断研究方向。
- [ ] 标题没有预设尚待检验的结论。
- [ ] 标题没有混入可移到介绍中的实现细节。
- [ ] 该节点表达的是科学未知，而不是 technique、object、application 或主题标签。
- [ ] 介绍说明了问题边界以及与相邻问题的区别。
- [ ] 当前进展覆盖全部 primary papers，并准确写出证据和限制。
- [ ] 没有把相关、可读、可定位或可操纵夸大为因果、忠实、完整或普遍。
- [ ] primary 与 secondary 归属符合论文真实侧重。
- [ ] 节点没有过度合并多个需要不同证据的问题。
- [ ] 关系线描述的是问题演化，并具有与证据等级匹配的措辞。
- [ ] 中英文内容自然、等价且证据强度一致。
- [ ] 修改已经通过结构校验、覆盖校验和网页数据构建。
