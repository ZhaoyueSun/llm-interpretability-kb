# Applications 分类与节点介绍写作审核准则

本文档约束 `data/taxonomies/application-scenarios.yaml` 的树结构、论文分类判断，以及各节点中英文 `introduction` 的写法。目标是让后续数据维护者在增加论文或修订节点时，始终依据实验任务进行分类，并为网页读者提供清楚、有研究意义的场景介绍。

这是面向后续 agent 和数据维护者的执行规范，不是 taxonomy 节点正文。

## 1. 这棵树回答什么问题

Applications 只回答：**论文在哪类任务、行为或实验场景中检验其可解释性结论？**

它必须与其他数据维度保持正交：

| 维度 | 回答的问题 | 不能混入 Applications 的内容 |
| --- | --- | --- |
| Research Objects | 研究模型内部的什么？ | attention head、neuron、residual stream、feature、representation |
| Techniques | 如何观察、验证或改变它？ | probing、SAE、patching、attribution、circuit discovery、steering |
| Contribution Role | 论文贡献是什么？ | method、theory、evaluation、empirical discovery |
| Model Family / Modality | 在哪类模型或数据模态上研究？ | Transformer、CNN、VLM、language、vision 本身 |
| Applications | 模型在实验中实际完成什么任务或表现什么行为？ | 上述技术、对象、贡献类型和架构标签 |

例如，一篇论文使用 SAE 分析 attention head，并在 IOI、Greater-Than 与 Docstring 数据上评测：SAE 属于 Techniques，attention head 属于 Research Objects；Applications 应按上下文使用、数学和代码任务表达。

## 2. 分类前必须检查的论文证据

不得仅依据标题、abstract、关键词或现有 Techniques / Research Objects 分类推断 Applications。逐篇判断至少检查：

1. Experiment Setup、Datasets、Tasks、Benchmarks、Evaluation 和 Case Study；
2. 主文没有写清时，继续检查实验附录和数据构造说明；
3. 数据集原本的用途，以及论文实际怎样改造和使用它；
4. 模型被要求产生什么输出，使用什么指标判断任务完成情况；
5. 该任务是支撑核心结论、用于主要验证，还是只作为 baseline、动机或零散示例。

数据集名称不能直接等同于场景。相同数据集可以承载不同任务，例如 COCO 图像既可以用于对象识别，也可以被改造成视觉问答或多模态幻觉评测。分类依据是论文实际执行的任务，而不是数据集最常见的标签。

## 3. Primary 与 Secondary

### 3.1 Primary

- 每篇论文在 Applications 中恰好有一个 primary。
- primary 是最能代表论文核心实证结论的任务族，不一定是样本数量最多的实验。
- 判断时优先看主要结果、核心因果验证和结论依赖的任务，而不是论文标题使用的行为词。
- 所有正式关系都应指向最具体且准确的叶节点。

### 3.2 Secondary

- secondary 记录主实验、主要稳健性实验或因果验证中实质使用的其他任务族，可以有多个。
- 仅在引言、相关工作、动机、普通 baseline 或单个 feature 展示中出现，不足以构成 secondary。
- secondary 不是把论文提到的所有主题全部罗列出来；它必须有可定位的实验数据和评价任务作为证据。
- 同一篇论文不能在同一个节点同时拥有 primary 与 secondary。

### 3.3 三类通用实验设置

- `General Language Modeling`：实验只使用通用文本和 next-token、future-token 或一般 feature analysis，没有更具体的下游任务。
- `Cross-Domain Task Suites`：论文有意在多个明显不同的任务族上检验同一结论。多个同类数据集不自动构成 cross-domain。
- `Synthetic Controlled Tasks`：数据专门为隔离规则、特征、状态或机制而生成，并以可控真值作为实验基础。

这三个节点描述实验设置，不得写成“通用可解释性方法”“方法评测”或“学习动力学”等贡献类型。

## 4. 节点命名与结构

- 标题使用英文，并优先采用可观察的任务或行为名称。
- 节点名称应让读者想到“模型被要求做什么”，而不是“模型内部表示了什么”。例如使用 `Language Understanding and Linguistic Tasks`，而不是容易被理解为研究对象的 `Linguistic Structure`。
- 不因模型是 VLM 就自动归入视觉问答；应继续判断实际任务是视觉识别、视觉问答、视觉推理还是多模态幻觉。
- 不因论文研究 truth direction、refusal direction 或 sentiment feature，就自动归入 Truthfulness、Safety 或 Sentiment；必须存在相应行为任务和实验评价。
- 父节点应组织一组具有共同研究问题的任务。若某节点只是技术、对象、模型族或论文属性，应移动到相应 tab，而不是继续扩充 Applications。
- 新增、移动、合并、拆分、重命名或废弃节点前，必须形成结构提案并获得用户批准。

## 5. Introduction 的读者定位

读者是对模型与可解释性有基本了解，但未必熟悉该任务领域的研究者。Introduction 应帮助读者理解：

1. 这类任务要求模型做什么；
2. 实验通常观察哪种能力、错误或行为；
3. 为什么值得从可解释性角度研究；
4. 研究内部机制可以帮助判断或改进什么。

介绍不是字段定义、论文列表、数据维护说明或分类规则。没有硬性字数，以完整回答上述问题且不重复为准。

## 6. 父节点与叶节点怎样分工

### 6.1 父节点

父节点应说明这一组任务共享的现实问题或科学问题，以及研究它们的总体价值。不要：

- 用“这一分支涵盖……”作为主要内容；
- 逐条枚举所有子节点；
- 写“各叶节点进一步区分……”；
- 解释论文如何分到 primary 或 secondary；
- 写当前 corpus 覆盖多少论文。

父节点可以自然描述多种信息来源或共同挑战，但应落到读者能理解的研究问题上。例如，Language, Knowledge, and Interaction 可以解释模型如何综合训练所得知识、上下文证据、语言关系和社会线索，以及这些来源如何影响理解与表达。

### 6.2 叶节点

叶节点应比父节点更具体，至少说明：

- 任务输入和期望行为；
- 该任务中最关键的能力或失效模式；
- 为什么仅看最终准确率不够；
- 机制分析能够揭示什么。

Reasoning 类叶节点尤其要说明为什么值得研究。例如数学任务适合把内部计算与已知求解过程对照；逻辑任务可以区分有效推理与启发式模式匹配；游戏提供状态和规则明确的受控世界；代码具有可执行语义，使许多错误可以直接验证。

## 7. 推荐的内容组织

Introduction 可以按以下顺序组织，但不要在正式正文中显示模板标签：

1. **任务**：模型在这种场景中需要完成什么；
2. **挑战**：该任务为什么困难，或什么错误值得关注；
3. **研究价值**：为什么需要理解内部机制，而不只看最终分数；
4. **可解释性价值**：机制研究能帮助区分、定位、验证或改进什么；
5. **必要边界**：只在容易误解时说明该节点不包含什么。

不要为了套模板机械地写满五部分。简单节点可以用两三句完成，复杂节点再增加必要解释。

## 8. Introduction 中禁止出现的维护话术

下列内容属于提案、事件流或维护文档，不得写入读者看到的 introduction：

- “这一分支”“这个节点”“各叶节点”等 taxonomy 导航语言；
- primary、secondary、proposal ID、taxonomy version、审批状态；
- 当前节点有多少篇论文、是否有 primary 论文；
- “为了展示 coverage gap 而保留”；
- “没有一个具体应用能够概括整篇论文”；
- “各项实际任务会作为 secondary 保留”；
- 对后续维护者的操作说明；
- 只服务于网页布局、筛选器或可视化展示的解释。

可以说明真实的学术边界。例如，区分视觉识别与视觉推理，或区分事实回忆与知识冲突，属于帮助读者理解任务，而不是内部维护话术。

## 9. 避免只罗列术语和数据集

- Introduction 不应变成 dataset 清单。数据集例子只在能帮助读者理解任务时出现。
- 不要用一串任务名代替共同问题的解释。先概括这类任务考察什么，再选择一两个代表性例子。
- 不要只写“包括算术、代数、数值比较”。还应说明研究这些任务为什么能够揭示模型是否进行系统计算、记忆答案或使用数值捷径。
- 不要把论文使用过的技术写进场景介绍，除非它是解释“机制研究可以做什么”的普通语言，而不是分类标签。

## 10. 中英文要求

- 中英文必须覆盖相同的任务范围、研究动机和解释边界。
- 不要求逐句直译，应分别符合自然中文和自然英文表达。
- 先向用户展示完整修订稿；未经批准，不得先写中文或英文任一版本到正式 taxonomy。
- 英文标题保持唯一且稳定，不额外维护中文标题。
- 方法名、benchmark 名和领域中稳定使用的英文术语可以保留，但不要让英文术语替代解释。

## 11. 修改与审批流程

1. 修改前读取当前节点、父子节点、相邻易混淆节点及其已分类论文。
2. 检查相关论文实验中的 datasets、tasks、benchmarks 和评价方式。
3. 判断问题属于分类关系、树结构还是 introduction 文案，三者不要混为一次隐式修改。
4. 向用户展示完整的中英文拟稿和必要的分类调整，不只描述“准备怎么改”。
5. 用户逐节点审核期间，只记录反馈，不修改正式 taxonomy、proposal 或事件流。
6. 只有用户明确表示“统一更新”“批准写入”等写入授权后，才执行正式修改。
7. Introduction 的实质修改写入 `data/classification-proposals.yaml`，记录批准依据、影响节点、版本变化和修改理由，并递增 taxonomy 版本。
8. 纯文案修改不改分类事件；关系变化只能向 `data/classification-events.jsonl` 追加事件，不得覆盖历史。
9. 修改前后运行校验，并只提交本次已批准文件，不得混入其他工作区改动。

讨论某个句子、指出问题或认可方向，不等于授权立即修改文件。若用户表示仍在逐节点审阅，必须等待统一批准。

## 12. 数据与结构检查清单

每次增加论文或改变分类时检查：

- [ ] 已阅读论文实验与数据部分，而不是只看标题和 abstract。
- [ ] 已确认数据集在该论文中实际承载的任务。
- [ ] 没有把 technique、research object、contribution role、model family 或 modality 当成 application。
- [ ] 每篇论文恰好有一个 primary，且指向有效叶节点。
- [ ] 每个 secondary 都有主实验或主要验证证据。
- [ ] 同一论文与节点没有 primary / secondary 重复。
- [ ] Cross-Domain、General Language Modeling 和 Synthetic Controlled Tasks 的使用符合各自条件。
- [ ] 分类理由和证据保存在提案与追加事件中。

## 13. Introduction 审核清单

每个新增或修改的 introduction 必须能回答“是”：

- [ ] 开头清楚说明模型在这类任务中要做什么，或面对什么问题。
- [ ] 说明了为什么该任务值得研究，而不只是罗列术语。
- [ ] 说明了可解释性研究能帮助理解、区分、定位或改进什么。
- [ ] 父节点表达共同研究问题，没有逐条复述子节点。
- [ ] 叶节点比父节点更具体，并有独立的研究价值说明。
- [ ] 没有使用“分支、节点、叶节点、primary、secondary、coverage gap”等维护语言。
- [ ] 没有写 corpus 数量、审批状态、可视化目的或更新指令。
- [ ] 没有把内部对象、方法或架构名称误写成应用场景。
- [ ] 中英文的范围、动机和结论强度一致。
- [ ] 已向用户展示完整拟稿，并在明确批准后才写入正式数据。

## 14. 典型改写模式

### Cross-Domain Task Suites

不写：

> 没有某一个具体应用能够概括整篇论文，各项任务会作为 secondary 保留。

应写任务价值：

> 跨领域研究会在多个明显不同的任务族上检验同一结论。这类实验可以帮助读者判断一项发现能否超越单个 benchmark、领域或数据模态而成立。

### Language, Knowledge, and Interaction

不写：

> 这一分支涵盖……各叶节点进一步区分……

应写共同研究问题：

> 语言模型生成回答时会综合训练中获得的知识、当前上下文提供的证据、语言中的结构与关系，以及语言或社会情境中的线索。研究这些任务，有助于理解不同信息来源如何影响模型的理解与表达。

### Reasoning and Formal Tasks

不只列出数学、逻辑、游戏和代码，还应说明：这些任务具有明确规则、中间步骤和正确答案，因此可以用来区分真正的规则计算、记忆和表面模式匹配，并解释模型在题目变化后为什么成功或失败。
